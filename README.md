# FHIR to OMOP Clinical Pipeline

Reproducible synthetic-data demo for loading FHIR R4 bundles into PostgreSQL and transforming them with dbt into a subset of OMOP CDM v5.4. The schema version follows the [OHDSI OMOP CDM v5.4 documentation](https://ohdsi.github.io/CommonDataModel/cdm54.html).

> **Scope:** this is an engineering demonstration, not a validated clinical system. Sample records are synthetic and Synthea-shaped. The checked-in data generator creates 100 patients and 700 FHIR resources. The demo maps the supported tables and does not implement every OMOP CDM field or vocabulary release.

## Quick start (Docker)

Requirements: Docker Desktop with Compose. From this directory:

```sh
cp .env.example .env
docker compose up --build
```

The pipeline container waits for PostgreSQL, applies idempotent schema DDL, ingests `data/fhir`, runs dbt models and dbt tests, then writes `quality-report.json` in the container. PostgreSQL is exposed on host port 5433 by default (override with `HOST_POSTGRES_PORT` in `.env`). Query the output with:

```sh
docker compose exec db psql -U clinical -d clinical -c 'select count(*) from omop.person;'
docker compose exec db psql -U clinical -d clinical -c 'select count(*) from omop.condition_occurrence;'
docker compose down
```

Re-run just ingestion or dbt with `make ingest` and `make dbt`. Generate a fresh synthetic dataset with `python scripts/generate_synthetic.py --patients 100 --output data/fhir`.

## Local development

```sh
python -m venv .venv && . .venv/bin/activate
pip install -e '.[dev]'
pytest -q
PYTHONPATH=src python -m fhir_omop.cli profile data/fhir --output quality-report.json
```

For PostgreSQL ingestion, start the `db` Compose service, set `DATABASE_URL` (see `.env.example`; host port 5433 by default), then run `fhir-omop ingest data/fhir`. Re-ingestion upserts by resource type and de-identified ID and skips unchanged payload updates.

## Data handling and semantics

- Configure `DEIDENTIFICATION_SALT` and `DATE_SHIFT_DAYS` for deterministic ID replacement and date shifts. These transformations are for synthetic data and are not a substitute for a reviewed de-identification process. Reference IDs are transformed consistently.
- Resource validation is structural. Invalid JSON/bundles and missing IDs raise errors rather than silently entering raw storage.
- Conditions, encounters, numeric and non-numeric observations, and procedures map to the corresponding OMOP table subset. Source codes remain in `*_source_value` fields.
- No vocabulary or OMOP concept IDs are bundled. `raw.terminology_map` is versioned by release; load authorized ICD-10-CM, SNOMED CT, LOINC, or RxNorm mappings and set `raw.pipeline_config` key `vocabulary_release` before use. Unmapped records retain source values and use concept ID `0`.
- `MedicationRequest` is a prescription/order. It is retained in `staging.medication_request` with `semantic_type='prescription_order'`; this pipeline does not infer confirmed medication administration or drug exposure.
- A quality report inventories resource counts, duplicates, rejected inputs, and source codes. Without a loaded terminology release, all inventoried codes are explicitly reported as unmapped.

## Architecture

See [`docs/architecture.mmd`](docs/architecture.mmd). Source layouts, transformation SQL, and database initialization are version-controlled for review.

Approved partner CSV rows can be written by the sibling onboarding app into `raw.partner_omop_staging`; dbt then includes those rows in `omop.person` and `omop.condition_occurrence`. Re-run the dbt pipeline after staging partner rows.

## Tests and CI

Python tests cover structural validation, deterministic identifier replacement, reference preservation, date shifting, and duplicate profiling. dbt tests cover key uniqueness, person relationships, future visits, and medication-order semantics. GitHub Actions runs pytest and validates Compose configuration.

## Limitations

- Docker/PostgreSQL/dbt end-to-end execution has not been verified in the current authoring environment if Docker is unavailable.
- OMOP output is a deliberately small v5.4 subset; production use requires fuller CDM DDL, terminology loading and validation, source-specific FHIR profiles, security review, and operational controls.
- Vocabulary licensing may restrict distribution of terminology data; no codes are shipped as concept mappings.
- The fixtures are representative FHIR-shaped synthetic resources, not output generated by the Synthea CLI. To regenerate via Synthea, use a Synthea release configured for FHIR R4 and replace the files in `data/fhir` with its bundles.
